## 🗂 Repository Structure

Every solved problem lives in its own top-level folder, named with its LeetCode problem number so the update workflow can match it back to LeetCode's own metadata automatically:

```text
leetcode-solutions/
├── 0001-two-sum/
│   └── Solution.java
├── 0011-container-with-most-water/
│   └── Solution.java
├── 0383-ransom-note/
│   └── Solution.java
├── ...
├── .github/
│   └── workflows/
│       └── update-readme.yml      # keeps everything below in sync
└── README.md                      # you are here
```

> Folder names only need to **start with the problem number** — `0383-ransom-note` and `1 Two Sum` are both matched correctly, since matching is done by number, not by parsing the title text.

## ⚙️ How This Stays Up to Date

This README is not maintained by hand. On every push to `main` (and on a weekly schedule as a safety net), a GitHub Actions workflow:

1. **Scans** the repository for numbered solution folders.
2. **Fetches** official problem metadata (difficulty, title, canonical slug) from LeetCode in a single bulk request.
3. **Matches** each folder to its problem by number — never by guessing a slug from the title.
4. **Fetches topic tags** only for problems not already cached, keeping API calls minimal on every run after the first.
5. **Rewrites** the stats and topics sections above, and commits the result.

See it in action: [`update-readme.yml`](.github/workflows/update-readme.yml) · [Actions history](https://github.com/Akshat983/leetcode-solutions/actions)
